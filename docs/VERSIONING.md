# 版本与发版规则

本项目遵循[语义化版本 2.0.0](https://semver.org/lang/zh-CN/)，版本号写在
`hwmon/__init__.py` 的 `__version__`。

## 三位数字各管什么

| 位 | 名称 | 什么时候 +1 | 例子 |
| --- | --- | --- | --- |
| 第一位 | 主版本 | **不兼容变更**：删功能、改配置格式导致旧配置失效、改命令行参数含义 | `1.1.1 → 2.0.0` |
| 第二位 | 次版本 | **新增功能**，且旧用法仍可用 | `1.0.2 → 1.1.0` |
| 第三位 | 修订号 | **只有修复**，没有新增功能，也没有行为变化 | `1.0.1 → 1.0.2` |

规则细节：

- 升次版本时，**修订号归零**（`1.0.2 → 1.1.0`，不是 `1.1.2`）
- 升主版本时，后两位归零
- 纯文档、纯 CI、纯注释改动**不升版本号**，也就不会触发发版
- 一次 PR 只做一类改动；若同时有功能与修复，按较高的那一位升

## 怎么判断该升哪一位

按顺序问自己：

```
1. 用户升级后，旧配置/旧用法会失效吗？
   会  → 主版本（X.0.0）
   不会 ↓

2. 用户能用上以前没有的东西吗？（新窗口、新指标、新设置项、新命令）
   能  → 次版本（X.Y.0）
   不能 ↓

3. 只是修 bug / 改性能 / 改文案？
   是  → 修订号（X.Y.Z）
```

## 发版流程

版本号是唯一的发版开关，改它即发版：

1. 修改 `hwmon/__init__.py` 的 `__version__`
2. 在 `CHANGELOG.md` 顶部添加本版条目，格式：

   ```markdown
   ## [1.1.1] - 2026-11-18

   ### 修复
   - 具体修了什么

   ### 新增 / 变更
   - （若没有则省略）
   ```

3. 更新 `RELEASE_NOTES.md`（这是 Release 页面正文）
4. 提交 PR

合并到 main 后，`Release` 工作流会自动：

- 检测版本号是否为新值（对应 tag 是否存在）
- 跑测试
- 用 PyInstaller 打包单文件 exe
- 计算 SHA256
- 创建 GitHub Release 并上传产物

**版本号没变则直接跳过**，不会重复发版。

## 不许做的事

- **不要修改已发布的 tag**。发错了就发下一个版本，不重写历史。
- **不要跳过版本号**（如 1.0.2 直接到 1.0.5）
- **不要在不改版本号的情况下期待发版**
- 修订号不要超过 9 就进位到次版本（`1.0.9 → 1.1.0`），避免版本号膨胀

## 版本历史中的特殊情况

本项目 `v1.1.0` 的体积比 `v1.0.0` 大（32.4MB vs 27.25MB），原因是打包配置把
`lib/` 目录重复收录了两次。这不是版本规则问题，在 `v1.1.1` 中修正。
